# Этап 3A: детерминированная обработка заявки

Вход: результаты парсинга и заранее подготовленные классификации и RawCandidate.
Выход: ProcessingResult и tuple[AuditEvent, ...]. Функция не читает и не записывает
файлы, не вызывает сеть, не изменяет входные модели и не генерирует DOCX.
Этот документ описывает самостоятельный слой бизнес-правил 3A. LLM, API, Streamlit, SQLite и экспорт реализованы в других слоях приложения.

## Вызов

```python
from document_automation.workflows.work_request_processing import process_work_request

result, events = process_work_request(prepared_input)
assert events == result.audit
```

`prepared_input` — WorkRequestInput из work_request_inputs.py:

- `run_id` — идентификатор текущего запуска;
- `sources` — RegisteredSource(run_id, source_id, parsed), созданные приложением;
- `classifications` — подготовленные ClassificationResult со свидетельствами;
- `fields` — RawFields с пятью скалярными полями заявки;
- `items` — RawItem(document_id, row, item_code, name, quantity, unit).

Каждое поле содержит tuple[RawCandidate, ...]. RawCandidate содержит `raw_value`
и заявленный `source: SourceFragment | None`. Пустое поле — пустой tuple.
Вход не принимает `verified`, интерпретации, итоговый статус или разрешения.
Регистрации и ParsedDocument — доверенные продукты приложения, не ответы модели.
Это граница доверия Python-библиотеки, не изоляция процессов и не авторизация.

RegisteredSource позволяет сопоставить вход запуску даже при ранней ошибке парсинга,
когда InputDocument ещё отсутствует. В 3A проверка выполняется над уже разобранными
данными; проверку до фактического чтения должен вызывать будущий слой ingestion.
Загрузчик и файловое разрешение путей в этом этапе не добавляются.

## Проверки источников и контекста

Классификация принимается только при допустимом соответствии типа формату и точном
совпадении evidence с фактическими фрагментами. Непроверенная классификация становится
unknown с проблемой. Смысловая классификация сама по себе остаётся подготовленным
входом: алгоритм классификации по содержанию здесь не реализован.

Кандидат сверяется с индексом фрагментов текущего запуска: document_id, fragment_id,
координаты и полный исходный текст. Проверяется допустимый тип источника поля.
Одного вхождения подстроки недостаточно:

- PDF/DOCX: точная подпись из demo contract в начале строки, двоеточие и полное
  значение после подписи (крайние пробелы допускаются);
- описание DOCX: явный верхнеуровневый раздел `Описание работ:`; таблица, следующая
  известная подпись либо заголовок с завершающим двоеточием завершает раздел;
- многоабзацное описание собирается в порядке документа только при покрытии всех
  непустых абзацев подтверждёнными кандидатами; исходные фрагменты сохраняются,
  пустые абзацы не теряются. Неполное покрытие даёт ambiguous и unsupported_content;
- дата XLSX: Заявка!B2 с проверкой подписи в A2;
- позиции: Работы!A:D, заголовки в строке 1, исходный номер строки со строки 2;
- XLSX: raw_value должен совпадать с полным текстом фрагмента, ячейка должна быть
  usable, а её fragment_id — соответствовать заявленному источнику.

Неподтверждённые кандидаты сохраняются с verified=false, пустыми interpretations
и исходным заявлением. Они не участвуют в выборе значения. Создаётся unverified_source;
поддельная ссылка не переносится в доверенные ValidationIssue.sources.

Подписи в неизвестных вариантах вёрстки и разделы без явных границ не угадываются.
Ссылка подтверждает происхождение текста, а не истинность утверждения документа.

## Нормализация и результат

Нормализация следует DEMO_CONTRACT.md. raw_value и source остаются неизменными.
Количество хранится как Decimal; для числовой Excel-ячейки используется stored_value,
если он есть. Boolean не считается количеством. Обычное число не считается датой:
принимаются предусмотренные текстовые форматы и типизированная дата Excel.
Для datetime Excel используется календарная дата, время не является бизнес-полем.

После исключения неподтверждённых кандидатов: нет кандидатов → missing; разные
однозначные значения → conflict; иначе наличие непреобразуемого свидетельства →
ambiguous; иначе равные однозначные значения → found. Конфликт имеет приоритет.
Равные названия заказчика сравниваются без регистра; для отображения PDF имеет
приоритет перед DOCX. Другие конфликты не разрешаются выбором источника.

Однозначные недопустимые значения (например, quantity=0, отрицательное количество,
неверная единица или email) сохраняют found, но получают invalid_value. Дата или
количество, не представимые целевым типом, сохраняют исходное свидетельство, получают
invalid_value и не имеют выбранного значения. Варианты трактовки не выдумываются.

Непустые строки берутся из структуры книги, а не только из списка RawItem:
пропущенная подготовленным извлечением строка сохраняется с missing-полями.
Пустые строки пропускаются; частичные сохраняются. Повторные нормализованные коды
дают ambiguous во всех затронутых строках. Формулы/объединения не используются.
Подготовленные строки вне фактической области источника отклоняются с диагностикой.

Несколько work_items не объединяются и не выбираются автоматически: позиции пусты,
выдаются duplicate_document и required_missing. Повторная регистрация одинакового
документа также является дублем; публичные ссылки по хешу сохраняются однократно,
регистрации различимы по source_id в audit. Несогласованные результаты парсинга
с одним document_id — техническая ошибка inconsistent_source_identity.

Проблемы объединяются по code/path с сохранением проверенных источников.
Для completed: needs_review = bool(issues). Отсутствующий необязательный email
не создаёт проблему. Ошибка парсинга/чужой запуск дают failed, data=None и запрет
генерации. Вход, нарушающий Pydantic-контракт (например, два RawItem для одной строки),
отклоняется ValidationError до обработки, а не маскируется бизнес-пропуском.

## Операции и audit

`operations.check_operation` — чистая проверка фиксированного условия.
`operations.audit_operation` — прикладная точка проверки: возвращает пару
OperationDecision и AuditEvent. Вызывающий код сохраняет событие; постоянного
хранилища в 3A нет. Обработка заявки использует эту точку для read_source и проверки
доступности create_draft; она не выполняет генерацию.

| Операция | Поведение 3A |
|---|---|
| read_source | Только зарегистрированный source_id данного run_id |
| create_draft | Только completed-результат того же запуска; draft_required отражает needs_review |
| modify_confirmed | prohibited_in_mvp |
| export_document | artifact_not_verified, даже если переданы метаданные GeneratedDocument |
| execute_external_action | prohibited_in_mvp |

Неизвестная операция явно отклоняется валидацией. Решение не исполняет операцию.
AuditEvent расширен event=operation_decision и необязательным decision; прежние
события остаются допустимыми. Отказ не является терминальным failed и не меняет
processing_status/needs_review. Решение и успешное выполнение — разные события.
Audit содержит коды и идентификаторы, без копирования исходного текста документов.

## Тестирование и ограничения

tests/business_samples.py строит новые синтетические входы, не читая ожидаемые
ProcessingResult из demo_contract.json. DOCX/XLSX создаются и читаются реальными
парсерами; большинство модульных сценариев используют снимок Unicode PDF на
границе ParsedDocument. Дополнительный test_scenario_a_with_real_pdf_docx_xlsx
читает настоящий tests/fixtures/business/customer.pdf через parse_pdf и передаёт
его вместе с реально разобранными DOCX/XLSX в 3A. Он проверяет completed,
needs_review=false, точное имя заказчика, подтверждения PDF и DOCX, email,
отсутствие unverified_source и неизменность байтов PDF. Все 233 теста проходят.
Это файловая интеграция парсеров с 3A; классификации и кандидаты подготовлены
тестом, LLM и генератор отсутствуют.

Проверяются A/B/C, нормализация, invalid_value, исключение кандидатов, неверные
координаты/контекст, конфликт с неоднозначностью, состав документов, строки XLSX,
технические ошибки, разрешения, audit, сериализация и отсутствие I/O.
Тесты не подтверждают полноту будущего извлечения: отсутствие предоставленного
скалярного кандидата не заменяется самостоятельным поиском значения. Нужны
отдельные интеграционные проверки при подключении извлечения в 3B.

Технические ограничения парсеров из PARSING.md остаются в силе. Хранилище audit,
проверка реальных артефактов и применение условий в API/UI отложены до этих этапов.
