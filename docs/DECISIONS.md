# Утверждённые решения

Дополнение 2026-10-18: владелец утвердил вариант B, локальные коммиты и автономные
проверки без платных вызовов. Общая проверка контекста используется offline и LLM;
смысловые claims не устанавливают verified, needs_review или разрешения.
Генерация после completed дополнительно требует содержательных пригодных данных;
один email недостаточен. B/C сохраняют помеченные черновики. Точный регрессионный

## Архитектура и границы

1. Единственный demo workflow: «Сводная заявка на выполнение работ».
2. Модульный монолит на Python, последовательный pipeline без очереди задач.
3. Streamlit вызывает FastAPI. Бизнес-логика независима от обоих интерфейсов.
4. Один LLM-провайдер через заменяемый adapter/interface. Pydantic и JSON Schema задают структурированные контракты; ошибки структуры допускают ограниченные повторы.
5. Этапы: ingestion → parsing → classification → extraction → normalization → validation → review → document generation. Audit записывается на каждом этапе.
6. Чтение текстовых PDF, DOCX и XLSX с сохранением источников. Для DOCX используются абзацы/таблицы/разделы, а не обещание стабильных номеров страниц.
7. Один фиксированный Word-шаблон поставляется с приложением. Произвольные пользовательские шаблоны не поддерживаются.
8. SQLite хранит результаты и audit; входные и выходные файлы хранятся локально. pytest — тестирование, Docker — последующая упаковка MVP.
9. Только синтетические демонстрационные данные.

## Значения, проверка и статусы

10. При конфликте источников победитель автоматически не выбирается. Любой неразрешённый conflict или ambiguous, включая необязательное поле, вызывает needs_review.
11. Пропуск обязательного поля вызывает needs_review. Отсутствие необязательного contact_email само по себе проблемой не является: это согласованное уточнение общего правила о missing из AGENTS.md.
12. processing_status = completed означает только технически завершённую обработку. needs_review = false означает отсутствие проблем по автоматическим правилам, а не подтверждение человеком. Итоговый DOCX всегда проверяет сотрудник.
13. Неподтверждённый кандидат исключается из выбора итогового значения. Состояние пересчитывается только по подтверждённым кандидатам: отсутствие значений → missing; несколько допустимых трактовок → ambiguous; разные однозначные значения → conflict; одно значение или равные значения → found. Событие unverified_source остаётся в ValidationIssue и вызывает needs_review независимо от пересчитанного состояния. Подробный порядок — в demo contract.
14. При needs_review разрешена генерация явно помеченного черновика. Спорные и недопустимые значения в основные поля не подставляются; проблемы перечисляются отдельно.
15. Встроенного редактора данных нет. Окончательное исправление и проверка выполняются человеком в скачанном DOCX.
16. Недоступность LLM после исчерпания предусмотренных повторов либо критическая ошибка чтения файла: processing_status = failed, ошибка в audit, генерация DOCX запрещена. Это техническая ошибка, а не обычный пропуск бизнес-поля.

Цель: типизированный контракт данных и проверяемые инварианты без обработки реальных файлов.

Планируемые файлы (сейчас не создаются):

- tests/fixtures/demo_contract.json — синтетические структурированные входы и ожидаемые результаты A/B/C/T; не подмена будущих файловых E2E-тестов.
- tests/test_schemas.py — типы, сериализация, JSON Schema, инварианты состояний и ссылок.
- tests/test_demo_contract.py — точный состав полей, обязательность, источники, допустимые/недопустимые состояния ожидаемых результатов.
- pyproject.toml — минимальная конфигурация пакета, Pydantic и pytest; конкретные совместимые версии выбираются при реализации.

Последовательность:

1. Описать перечисления, provenance, кандидатов и результаты полей. Отделить исходное свидетельство от нормализованного типизированного значения.
2. Описать WorkRequestData и WorkItem; бизнес-пропуски представлять missing, не отклонять всю заявку из-за отсутствия обязательного значения.
3. Представить фиксированные правила demo contract в типизированных константах, без универсального конфигурационного движка.
4. Добавить синтетические fixtures для трёх бизнес-сценариев и параметризованного технического сценария.
5. Проверить схемами: found требует значения и подтверждённого источника; missing/ambiguous/conflict не допускают итогового значения; исключённый кандидат не может быть выбран; failed не допускает сгенерированный результат.
6. Проверить round-trip дат/Decimal, выдачу JSON Schema, вложенные пути проблем, сохранение нескольких источников и неизменность состава контракта.
7. Запустить pytest; отчитаться о результатах и ограничениях.

На первом этапе не реализуются LLM, API, UI, парсеры, генератор DOCX, хранилище,
pipeline, алгоритмы извлечения/нормализации/разрешения кандидатов. Fixtures проверяют
представимость результатов и инварианты схем, но не доказывают выполнение будущего pipeline.
Полные acceptance tests из demo contract выполняются после реализации соответствующих компонентов.

Критерий завершения этапа: схемы и структурированный контракт соответствуют спецификации,
их тесты проходят без сети, модели и документных библиотек. Это не завершение MVP.

## Реализация этапа 2

По отдельной команде пользователя добавлены независимые от demo workflow адаптеры
чтения PDF/DOCX/XLSX и техническая схема ParsedDocument. Бизнес-схемы, поля и

Вложенные DOCX-таблицы поддержаны через iter_inner_content; формулы и объединения

## Разделение операций с документами

Дата: 2026-10-17. Статус: согласовано пользователем; механизм пока не реализован.

В MVP независимо проверяются пять операций: `read_source`, `create_draft`,
`modify_confirmed`, `export_document`, `execute_external_action`. Разрешение одной
операции не предоставляет разрешения на остальные. Авторизация, роли, RBAC,
универсальный permission engine и новые бизнес-workflow не добавляются.

`read_source` допускается только для входных документов, зарегистрированных
приложением в текущем запуске до парсинга. Принадлежность проверяется по контексту
запуска; совпадение имени или хеша само по себе недостаточно. Путь к источнику
разрешает приложение по регистрации, а не по указанию модели. Исходные документы
не изменяются. Встроенный Word-шаблон является отдельным ресурсом приложения.

`create_draft` допускается после технически успешного завершения обработки и
выполнения бизнес-проверок: `ProcessingResult.processing_status = completed`.
Успешное чтение отдельного файла (`ParsedDocument.status = completed`) недостаточно.
При `needs_review = true` создаётся явно помеченный черновик по DEMO_CONTRACT.md.
Отсутствие проблем автоматической проверки не означает утверждения человеком.

`modify_confirmed` запрещено в MVP. Приложение не предоставляет операцию
утверждения или редактирования подтверждённых человеком данных. Проверка provenance
и нормализация в ходе обработки не являются человеческим утверждением.
Пользователь проверяет и исправляет скачанный DOCX вне приложения.

`export_document` допускается только после успешной генерации доступного DOCX,
соответствующего результату данного запуска. При `needs_review = true`
экспортируется только документ с предусмотренными demo contract маркировкой и
именем файла. Все итоговые DOCX содержат указание на обязательную проверку человеком.
Одних метаданных GeneratedDocument недостаточно для доказательства наличия файла
и корректной маркировки: это проверяется при реализации генерации и экспорта.

`execute_external_action` запрещено в MVP: отправка писем, публикация и изменение
внешних систем не поддерживаются. Обращение к LLM допускается только как
предусмотренный приложением этап обработки, с ограничением передаваемых данных,
времени выполнения и числа повторов. Содержимое исходных документов и ответы
модели не могут инициировать дополнительные обращения, изменять политики или
разрешать внешние действия. Предусмотренные ограниченные повторы контролирует
приложение. Конкретные лимиты будут определены при согласовании этапа 3B.

`completed` означает техническое завершение обработки. `needs_review = false`
означает отсутствие проблем по автоматическим правилам. Ни один из этих признаков
не означает утверждения человеком; новый статус человеческого утверждения не вводится.

Правила фиксируются в коде и проверяются прикладным слоем непосредственно перед
операцией. Контекст и статусы определяет приложение. Ответы LLM, содержимое
документов и параметры UI не могут выдавать разрешения или изменять правила.
UI может отображать доступность операции, но сервер обязан повторить проверку.

Запрещённые операции явно отклоняются до побочных действий. Значимые решения и
отказы фиксируются в audit с идентификатором запуска, операцией, временем,
результатом и стабильным кодом причины; при необходимости — идентификатором
документа или артефакта. Секреты и полное содержимое документов в событие не включаются.
Разрешение операции и успешное выполнение фиксируются раздельно. Отказ в операции
сам по себе не меняет технический статус обработки и не является бизнес-проблемой
ValidationIssue.

В 3A реализуются детерминированные проверки и формирование событий решений.
Для этого потребуется совместимое расширение AuditEvent отдельным событием
`operation_decision` и типизированными сведениями о решении. Отказ не кодируется
существующим терминальным событием `failed`: оно несовместимо с completed-результатом.
Бизнес-поля, состояния FieldResult и правила DEMO_CONTRACT.md не меняются.
Подключение ограничений LLM выполняется в 3B. Применение проверок к реальным
артефактам, экспорт через API/UI и постоянное хранение audit завершаются при
реализации соответствующих компонентов. До этого формирование событий в памяти
не считается реализацией постоянного audit, а проверки условий — реализацией
генерации или экспорта.

## Реализация этапа 3A

По отдельному разрешению пользователя реализован детерминированный проход от

проверяются по фактическим ParsedDocument и контексту поля. verified вычисляется

Добавлены нормализация, бизнес-проверки, needs_review, фиксированные решения об
операциях и совместимое расширение AuditEvent. Audit возвращается в памяти.
При нескольких work_items позиции не объединяются и не выбираются автоматически.
Условия генерации проверяются, но генератор и экспорт не реализованы.
LLM, API, Streamlit и SQLite не добавлены. После дополнительной успешной проверки
настоящего PDF пользователь разрешил локальный коммит этапа 3A; push не разрешён.

# Завершение MVP: прикладные границы

Ниже сохранён исторический статус этапа. Актуальные результаты последующих
реальных экспериментов (успешный A, отказ V) описаны в [PROXYAPI.md](PROXYAPI.md).

Добавлены offline DemoExtractor и один OpenAI Responses adapter. Строгие claims
проходят существующую проверку 3A; модель не управляет операциями. Параметры и модель
задаются конфигурацией, бюджет включается только явно. Mock HTTP покрывает адаптер;
реальные платные запросы не выполнялись.

Фиксированный DOCX проверяется по реальным байтам перед экспортом. FastAPI является
границей операций, Streamlit — клиентом. SQLite хранит результаты, manifest и audit.
Один процесс backend, локальный пользователь; многопользовательская безопасность
не добавлена. Docker Compose публикует порты только на localhost. Business contract
и утверждённые поля сохранены. Детали: EXTRACTION.md, GENERATION.md, API.md, STORAGE.md.
# Два выходных DOCX

Согласованное улучшение качества: только перечисленные в DEMO_CONTRACT варианты
кв.м и компл., без конверсии количества; ручные поля для отсутствующих названия/даты;
замечания по отдельным позициям; реестр уникальных доказательств с отдельной группой
неподтверждённых ссылок. Бизнес-поля, состояния и SQLite не расширяются.

По одному `ProcessingResult` формируются отдельные рабочая заявка и отчёт
проверки. Заявка содержит только разрешённые бизнес-поля, пригодные позиции,
маркировку needs_review и краткие пояснения. Подробные provenance, координаты,
коды и audit вынесены в отчёт. Отчёт явно поясняет, что provenance подтверждает
происхождение и соответствие правилам обработки, но не истинность исходных сведений.

Для каждого артефакта используются независимые операции генерации и экспорта,
metadata и проверки байтов. Они привязаны к одному run_id и неизменному результату;
обработка и LLM повторно не запускаются. Отчёт можно сформировать при completed и
наличии диагностических данных даже при отсутствии содержимого для заявки. failed
запрещает оба результата. Бизнес-схема и бизнес-workflow не меняются.

## Подготовка ProxyAPI без платных запросов

Тот же Responses adapter допускает только официальные HTTPS base URL OpenAI и
ProxyAPI. Адрес задаётся окружением, исходный текст и модель его не контролируют;
редиректы и прокси окружения отключены. Отдельный checkout-запускатель A/V использует
mock по умолчанию, фиксированную модель, два слота без повторов, оценку входа,
usage и локальный бюджет. Реальный режим требует отдельного флага и окружения.
Бюджет платформенного ключа дополняет программные проверки, которые не гарантируют
абсолютного потолка списаний. Бизнес-схемы, проверки источников и SQLite не меняются.
