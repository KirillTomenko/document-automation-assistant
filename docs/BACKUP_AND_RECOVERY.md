# Backup, Verify, Restore — этап 8

Числа тестов в исторических разделах относятся к соответствующему этапу; текущая проверка кандидата — [RELEASE_CANDIDATE_REPORT.md](RELEASE_CANDIDATE_REPORT.md).

Локальная копия **данных**, без внешнего сервиса, расписания, облака и шифрования.
Используйте ту же версию приложения и шаблона DOCX. Проверена Windows / локальный
NTFS. Для первой версии backend должен быть остановлен; все операции завершены
или явно восстановлены. Контракты work_request/1.0 и 2.0 не меняются.

## Сначала остановите приложение

1. Дождитесь окончания текущей обработки и выпуска DOCX. Не отправляйте новые файлы.
2. В окне PowerShell с uvicorn нажмите **Ctrl+C один раз** и дождитесь завершения
   shutdown и появления приглашения PowerShell. Закрытия одной вкладки Streamlit
   недостаточно: backend — отдельный процесс. Можно остановить и Streamlit через Ctrl+C.
3. Если процесс был аварийно прерван, сначала запустите приложение, проверьте
   состояние запуска и DOCX. Незавершённый выпуск восстановите по
   [ARTIFACT_RECOVERY.md](ARTIFACT_RECOVERY.md), затем корректно остановите backend.
   Не создавайте новый платный запуск ради backup.

Backend удерживает локальный файловый замок в течение FastAPI lifespan. CLI backup
требует эксклюзивного доступа; даже бездействующий работающий backend даёт data_busy.
Инициализация сервиса, SQLite-доступ и полные операции обработки/генерации также
участвуют в блокировке. Во время копирования новый backend на этих данных не стартует.
Это один локальный файловый замок, не распределённая инфраструктура.

Рядом с каталогом данных находится `.daa-data-<hash>.lock`, вне самой копируемой
директории. Нужны права записи в родительский каталог. Наличие этого маленького
файла не означает занятости: проверяется блокировка ОС. После штатного завершения
или смерти процесса ОС освобождает её. **Не удаляйте lock-файл для обхода data_busy.**
Не отключайте lifespan и не используйте несколько workers, старый backend без
этого протокола или сторонние редакторы SQLite во время обслуживания.

## Создать и проверить копию

Откройте PowerShell в рабочем проекте:

```powershell
# Выполняйте из корня вашего checkout Document Automation Assistant.
$env:PYTHONPATH = 'src'
New-Item -ItemType Directory -Force -Path .\backups | Out-Null
$backupStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$backupPath = Join-Path (Join-Path (Get-Location) 'backups') $backupStamp
python -B -m document_automation.backup backup --data .\data --output $backupPath
if ($LASTEXITCODE -ne 0) { throw 'Копия не создана. Прочитайте безопасный код ошибки.' }
python -B -m document_automation.backup verify-backup --backup $backupPath
if ($LASTEXITCODE -ne 0) { throw 'Копия не прошла проверку.' }
```

Если DAA_DATA_DIR указывает на другой каталог, замените `--data .\data` на его путь.
Родительский каталог output должен существовать; сам output — **новый путь, которого
ещё нет**. Даже существующий пустой каталог не заменяется: это намеренное правило
первой версии для публикации без перезаписи. Не создавайте каталог `$backupPath`
заранее. Команда создаёт его после успешной проверки.

Успех — JSON со status=ok, format_version=1, количеством запусков, файлов,
исходников и каждого вида DOCX. Код завершения 0. Ошибка — status=error,
безопасный code/detail и код завершения 1. Содержимое документов, ключи, prompts
и сырые ответы провайдера не выводятся в диагностику.

Внутри готового каталога находятся manifest.json, manifest.sha256, workflow.sqlite3
и файлы в прежних относительных каталогах run_id. verify-backup независима от
работающего backend и не запускает извлечение или восстановление 7B.

## Что входит и как проверяется

Включаются:

- согласованный снимок всей штатной SQLite через **sqlite3.Connection.backup**;
- зарегистрированные файлы из `<run_id>/inputs/`;
- каждый уже подтверждённый DOCX заявки и отчёта;
- в SQLite: исходные snapshots v1/v2, provenance, audit, metadata, idempotency keys
  (их хеши), retry_of, llm_runs/llm_attempts с usage, тарифами, оценками и неизвестными
  расходами, весь artifact_writes с прежними metadata и состояниями.

Не включаются .env, API-ключи из окружения, код проекта, посторонние файлы и
временные материалы. Байты `.artifact-recovery` этапа 7B также **не входят**:
это неподтверждённые/повреждённые материалы изоляции, не готовые результаты.
История abandoned и прежние metadata сохраняются в SQLite. Backup восстанавливает
рабочее состояние приложения, не является полной forensic-копией каждого файла data.
Оригинальная изоляция не удаляется и не изменяется.

Проверки перед созданием и при verify-backup:

- нет snapshot=NULL, активных registered/processing запросов, started LLM-попыток,
  prepared artifact_writes и оставшихся файлов незавершённой генерации;
- нет SQLite -wal, -shm, -journal: первая версия отказывает, пока они есть;
  не удаляйте их вручную, требуется корректное восстановление/закрытие SQLite;
- штатная схема с известными таблицами/колонками/ключами; без посторонних таблиц,
  views и triggers; integrity_check и foreign_key_check;
- digest и строгая Pydantic-проверка каждого сохранённого результата, audit,
  журналов, связей run_id, retry_of, метаданных документов и артефактов;
- SHA-256 исходников и DOCX; для DOCX дополнительно прежняя проверка содержимого,
  run_id, fingerprint, шаблона или audit_snapshot. Открытия ZIP недостаточно;
- версия manifest, его отдельная контрольная сумма, перечень/размер/SHA-256 каждого
  файла, совпадение перечня с SQLite. В копии запрещены лишние файлы и пустые каталоги;
- пути относительные, без `..`, drive/UNC/ADS, Windows device names и конфликтов
  регистра; symlinks, junctions/reparse points и hard links запрещены.

Если DOCX ещё никогда не выпускался, отсутствие metadata — допустимый not_generated;
проверка не создаёт его автоматически. Если metadata уже есть, отсутствующий или
повреждённый DOCX блокирует backup и требует явного восстановления 7B.

Неопределённое **локальное** состояние блокирует копирование. Историческая неизвестная
стоимость или неизвестный удалённый исход в уже сохранённом terminal failed-запуске
сохраняется как неизвестная: это не started/активная операция и не разрешение повторить
LLM-вызов. CLI не выясняет состояние у провайдера и не подменяет расход нулём.

Оригинал открывается только для чтения (без DDL, миграций и автоматического recovery).
Backend/операции заблокированы на всё время; SQLite backup API создаёт снимок,
файлы копируются по списку SQLite как новые байты, затем выполняется полная проверка.
Дополнительно повторно проверяются оригинальные файлы и неизменность байтов исходной
БД. Новый manifest описывает снимок SQLite: SHA-256 файла снимка может отличаться
от исходного файла БД при сохранении всех логических записей.

Создание идёт в соседнем `.<имя>-staging-<случайный id>`. Только проверенный каталог
атомарно переименовывается в новое конечное имя на том же томе, без замены существующего.
Если ошибка возникла при копировании или проверке, готового backup не появляется. Незавершённый staging может
остаться для диагностики; не используйте его как копию и защищайте доступ к нему.

## Восстановить в отдельный каталог

Backend и Streamlit остаются остановленными. Выберите новый путь:

```powershell
New-Item -ItemType Directory -Force -Path .\data-restored | Out-Null
$restoredPath = Join-Path (Join-Path (Get-Location) 'data-restored') ('check-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
python -B -m document_automation.backup restore --backup $backupPath --target $restoredPath
if ($LASTEXITCODE -ne 0) { throw 'Восстановление не опубликовано.' }
```

Сам `$restoredPath` не должен существовать; команда создаёт его. Текущий data не
перезаписывается. Источник и назначение не могут быть вложены друг в друга.

Сначала проверяется копия. Файлы создаются заново в соседнем staging, без сохранения
ссылок на исходные inode/NTFS file records. Снова проверяются SHA-256, SQLite,
зарегистрированные источники, v1/v2 и оба подтверждённых DOCX. Проверяется отсутствие
лишних путей. До публикации исходная копия проверяется ещё раз. При ошибке target
остаётся отсутствующим при отказе до публикации; существующий каталог назначения не изменяется.

Если на месте target появляется другой каталог в процессе работы, публикация
отказывается от выполнения. Symlinks/junctions не обходят проверку, hard-linked
файлы исходной копии отвергаются. Файлы восстановления имеют отдельные данные,
а не являются жёсткими ссылками на backup. Staging после неудачи не готов к запуску.

Если процесс прерван уже после успешного переименования, он может не успеть показать
status=ok. Готовую копию сначала проверьте через verify-backup; восстановленные данные —
через запуск приложения и проверку прежних run_id/DOCX. Существующий каталог не заменяйте
повторной командой: она честно откажет с target_exists.

## Проверить восстановленное приложение

В этом окне PowerShell запустите backend на восстановленных данных:

```powershell
$env:DAA_DATA_DIR = $restoredPath
$env:DAA_MODE = 'demo'
$env:DAA_ALLOW_PAID = 'false'
python -B -m uvicorn document_automation.api:create_app --factory --host 127.0.0.1 --port 8000 --lifespan on
```

Режим demo позволяет проверить сохранённые результаты без платных вызовов. Чтение
старой LLM-истории не пересчитывает тарифы. Не нажимайте новое действие обработки
ради проверки восстановления. В другом окне PowerShell:

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/health'
$savedRunId = 'ВСТАВЬТЕ_ПРЕЖНИЙ_32_СИМВОЛЬНЫЙ_RUN_ID'
Invoke-RestMethod "http://127.0.0.1:8000/runs/$savedRunId"
Invoke-RestMethod "http://127.0.0.1:8000/runs/$savedRunId/usage"
Invoke-RestMethod "http://127.0.0.1:8000/runs/$savedRunId/artifacts"
Invoke-WebRequest "http://127.0.0.1:8000/runs/$savedRunId/document" -OutFile .\tmp\restored-work-request.docx
Invoke-WebRequest "http://127.0.0.1:8000/runs/$savedRunId/verification-report" -OutFile .\tmp\restored-verification-report.docx
Get-FileHash -Algorithm SHA256 .\tmp\restored-work-request.docx
Get-FileHash -Algorithm SHA256 .\tmp\restored-verification-report.docx
```

Используйте run_id с ранее выпущенными документами из технических подробностей
запуска; он также присутствует в manifest.results. Сравните хеши с прежними metadata
generated_document.sha256 и generated_report.sha256. При необходимости создайте
каталог tmp заранее. Источники сохраняются внутри восстановленного каталога.
Второй интерфейс можно открыть обычным запуском Streamlit на localhost.

Экспорт законно добавляет событие audit, поэтому после скачивания digest всего
snapshot может измениться. Бизнес-fingerprint, исходники и DOCX остаются прежними.
API-повтор с тем же ключом и содержимым возвращает прежний run_id без обработки.
Закройте проверочный backend перед любой следующей копией/восстановлением.

## Коды отказа и защита копии

data_busy — остановите backend/операции, не обходите lock. recovery_required —
завершите восстановление 7A/7B. sqlite_sidecars_present — проверьте корректное
закрытие SQLite. target_exists — выберите новый путь. Коды checksum/inventory,
sqlite_integrity, unsupported_schema и backup_validation_failed означают, что
копию/данные нельзя использовать до выяснения причины. Исходные данные не исправляются
этими командами; повреждённый manifest не «чинится» пересчётом его SHA.

Копии содержат исходные документы и бизнес-данные: ограничьте права чтения каталога
через Windows «Свойства → Безопасность». Не используйте общие сетевые каталоги и
автоматически синхронизируемые папки. backups/, data-restored/ и lock-файлы исключены
из Git; не добавляйте их принудительно. Для других путей самостоятельно исключите
их из публикации. Шифрования и автоматического управления ACL здесь нет.

Копия на **том же физическом диске не защищает от отказа этого диска**. Для защиты
от такой аварии нужна отдельная защищённая копия на другом носителе и повторный
verify-backup после переноса. Автоматического облачного копирования нет.

Контрольные суммы выявляют повреждение и несогласованность, но не являются цифровой
подписью. Полную согласованную подмену всех файлов и manifest администратором с правом
записи без внешнего доверенного эталона обнаружить нельзя. Приватные каталоги и
отсутствие параллельного ручного редактирования — условия этого локального MVP.
Защита от полного отказа носителя, любой аварии питания или злонамеренного администратора
не обещается. Копия кода/окружения, межверсионная миграция и смена ОС не реализуются.

## Фактическая синтетическая демонстрация

```powershell
$env:PYTHONPATH = 'src'
python -B scripts/demo_backup_restore.py --output .\tmp\backup-restore-demo
```

Output должен быть новым путём. Скрипт создаёт v1 offline и v2 mock-запуски, включая
явный retry_of и timeout с неизвестной стоимостью. Он дважды запускает настоящий
uvicorn на localhost: до копии и после восстановления. Остановка штатная через
should_exit; команды CLI выполняются отдельными процессами. Реальных LLM-вызовов нет.

Фактически выполнено на окончательном формате: tmp/stage8-final-demo/summary.json — 4 запуска,
6 исходников, 2 заявки и 2 отчёта. Все 10 файлов документов совпали по SHA-256;
snapshots до экспорта, business fingerprints, idempotency, retry_of и usage совпали.
API читает прежние run_id и выдаёт DOCX. Оригинальная БД осталась побитово прежней.
Работающий backend, повреждённая копия и занятый target вызвали отказ. Три обращения
к модели — только httpx.MockTransport, usage/тарифы симулированные; внешних вызовов 0.

Подтверждено 20.10.2026: **652 passed**, 423,88 с, полная регрессия командой
`python -B -m pytest -q -p no:cacheprovider --basetemp=tmp/stage8-final-full-regression`.
Из них 62 новых проверки: backup/restore v1/v2, idempotency/usage/retry_of,
unknown cost, активный backend (включая отдельный процесс), незавершённые операции,
повреждение/потеря файла, подмена/reseal/неполнота manifest, bool/пропущенная версия,
SQLite integrity/FK/audit, NTFS junction и hard link, временные/посторонние файлы,
ошибки копирования/публикации, изменение БД после снимка, сохранность занятого target
и отсутствие утечки содержимого в CLI-ошибку. Одно прежнее предупреждение Starlette.
Ruff check/format (72 файла), check_repository.py и git diff --check прошли.

Технические основания: [SQLite backup API Python 3.12](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup),
[SQLite immutable URI](https://www.sqlite.org/uri.html),
[msvcrt.locking](https://docs.python.org/3.12/library/msvcrt.html#msvcrt.locking),
[NTFS hard links и junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).

## Совместимость с этапом 9

Текущая проверка схемы также поддерживает `acceptance_events` и проверяет историю
принятия/отзыва. Журнал целиком сохраняется внутри штатного снимка SQLite, как расходы,
idempotency и audit; формат manifest и порядок backup/verify/restore не изменены.
Копии этапа 8 без новой таблицы поддерживаются. Для новых копий используйте текущую
версию приложения: прежний verifier этапа 8 отклонит неизвестную ему таблицу.
Подробности: [BUSINESS_METRICS.md](BUSINESS_METRICS.md).
