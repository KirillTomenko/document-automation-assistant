# Demo contract: Сводная заявка на выполнение работ

Дополнение от 2026-10-18: исходные A/B/C и бизнес-поля сохранены. Разрешённые
вариации источников и дополнительный порог содержательности генерации описаны в
[VARIANT_B.md](VARIANT_B.md). Эти правила расширяют примеры точных подписей,
имён листов и фиксированных колонок ниже, не меняя нормализацию и needs_review.

Дата: 2026-10-16. Версия: 1.0. Статус: согласовано до реализации.
Архитектурные решения: [DECISIONS.md](DECISIONS.md).
Scope: [PROJECT_BRIEF.md](../PROJECT_BRIEF.md); правила: [AGENTS.md](../AGENTS.md).

## 1. Вход и результат

Один корректный комплект содержит ровно три исходных документа, загружаемых в произвольном порядке:

| Тип | Формат | Содержание |
|---|---|---|
| customer_card | Текстовый PDF | Заказчик, контактный email |
| work_description | DOCX | Название заявки, заказчик, описание работ, желаемая дата завершения |
| work_items | XLSX | Желаемая дата завершения и перечень работ |

Классификация определяется содержанием, не именем файла. Один фиксированный Word-шаблон
поставляется с приложением. Сценарий — подготовка офисной комнаты; данные только синтетические.
Результат — DOCX для обязательной проверки сотрудником, источники значений и audit.
Встроенного редактора нет; человек исправляет скачанный DOCX.

## 2. WorkRequestData

Скалярные поля представлены FieldResult[T]: state, value либо None, кандидаты и источники.
items — список WorkItem с состоянием контейнера found/missing; непустой список сохраняет
все строки и их проблемы. Пустой список имеет missing. ID запуска, статусы, ошибки и время
относятся к ProcessingResult, а не к бизнес-полям.

| Поле | Тип значения | Обязательность | Допустимые источники |
|---|---|---|---|
| customer_name | str | Да | PDF «Заказчик»; DOCX «Заказчик» |
| request_title | str | Да | DOCX «Название заявки» |
| work_description | str | Да | DOCX раздел «Описание работ» |
| requested_completion_date | date | Да | DOCX «Желаемая дата завершения»; XLSX Заявка!B2 |
| contact_email | str | Нет | PDF «Контактный email» |
| items | list[WorkItem] | Да, минимум одна строка | XLSX лист Работы |

Обязательное значение достаточно найти хотя бы в одном допустимом источнике.
Отсутствие повторного упоминания не является проблемой. Значения из не предусмотренных
для поля источников не используются. Других бизнес-полей нет.

## 3. WorkItem и структура XLSX

Каждая ячейка представляется FieldResult[T]; номер строки сохраняется как provenance.

| Поле | Тип | Обязательность | Колонка листа Работы |
|---|---|---|---|
| item_code | str | Да | A: Код позиции |
| name | str | Да | B: Наименование работ |
| quantity | Decimal | Да | C: Количество |
| unit | str | Да | D: Единица |

- Лист Заявка: A2 = «Желаемая дата завершения», B2 = значение.
- Лист Работы: заголовки в строке 1, позиции со строки 2.
- Полностью пустые строки пропускаются; частично заполненные сохраняются и проверяются.
- Порядок строк сохраняется. Источник позиций единственный; объединения между документами нет.
- Код позиции уникален в книге. Повторный код даёт ambiguous во всех затронутых строках; строки не удаляются и не объединяются.
- Формулы и объединённые ячейки в области данных не поддерживаются: unsupported_content и needs_review. Значение такой ячейки не используется.

## 4. Нормализация

Исходный фрагмент всегда сохраняется. Нормализация не дополняет данные догадками.

| Поле | Правило |
|---|---|
| customer_name | Убрать крайние пробелы, заменить неразрывные пробелы обычными, свернуть повторяющиеся пробелы; сравнивать без учёта регистра. Не исправлять название, не расшифровывать сокращения, не удалять организационную форму |
| request_title | Убрать крайние пробелы, свернуть переносы и последовательности пробелов в один пробел |
| work_description | Сохранить абзацы и формулировки; убрать крайние пробелы абзацев, нормализовать пробелы внутри; не пересказывать |
| requested_completion_date | Принимать ДД.ММ.ГГГГ, ГГГГ-ММ-ДД и дату Excel; хранить date, отображать ДД.ММ.ГГГГ |
| contact_email | Убрать крайние пробелы, привести домен к нижнему регистру; проверить форму имя@домен без пробелов и с точкой в домене; существование адреса не проверять |
| item_code | Убрать крайние пробелы, латинские буквы привести к верхнему регистру; допустимы латинские буквы, цифры и дефис |
| name | Убрать крайние и свернуть повторяющиеся пробелы; сохранить формулировку |
| quantity | Число Excel либо строка с целым числом или десятичным разделителем запятая/точка; хранить Decimal; значение больше нуля |
| unit | Убрать крайние пробелы, нижний регистр; шт. → шт; час/часов → ч; кв.м / кв. м / кв.м. / м2 / м² → кв.м; компл / компл. / комплект / комплекта / комплектов → компл.; допустимы только шт, ч, кв.м, компл. |

Список соответствий единиц конечный. Исходное написание сохраняется в raw_value
и provenance, итоговое — в существующем поле unit. Количество не пересчитывается,
единица не выводится из описания; остальные единицы (включая м³) недопустимы.

Разделители тысяч, преобразование единиц и вывод количества из описания не поддерживаются.
Неоднозначная дата вроде 03/04/2026 не интерпретируется автоматически.
Дата не проверяется относительно сегодняшнего дня.

customer_name и requested_completion_date намеренно повторяются в двух источниках.
Равные после нормализации значения дают found с сохранением обоих источников.
Для отображения равных названий используется написание в порядке PDF → DOCX;
это не правило разрешения конфликтов.

## 5. Состояния и неподтверждённые источники

| Состояние | Условие | value |
|---|---|---|
| found | Одно однозначное значение либо несколько равных нормализованных значений | Значение |
| missing | Нет подтверждённых значений; пустая ячейка означает отсутствие | None |
| ambiguous | Несколько допустимых трактовок, невыбранные альтернативы либо невозможность однозначного преобразования | None |
| conflict | Два или более разных однозначных нормализованных значения | None |

Детерминированный порядок:

1. Проверить ссылки кандидатов на существующие исходные фрагменты и наличие указанного свидетельства.
2. Неподтверждённый кандидат исключить из выбора value. Сохранить ValidationIssue с кодом unverified_source и привязкой к полю. Исключённый кандидат не считается доказательством.
3. Пересчитать состояние только по оставшимся подтверждённым кандидатам: если их нет — missing; если есть разные однозначные значения — conflict; иначе при наличии неразрешённых трактовок — ambiguous; иначе — found.
4. Доказанный conflict имеет приоритет над дополнительной неоднозначностью. Однозначный кандидат не отменяет неоднозначное свидетельство из другого источника.
5. unverified_source сохраняется независимо от пересчитанного состояния и всегда приводит к needs_review. Например, после исключения ложного кандидата поле может стать found, но проблема остаётся.

Проверка допустимости отдельна от состояния извлечения: однозначно найденное quantity = 0
может иметь found, но получает invalid_value и не попадает в DOCX. Некорректное значение,
которое нельзя представить целевым типом, не должно обрушать всю заявку: сохраняются
исходный кандидат, проблема и отсутствие выбранного значения.
Дубли item_code дополнительно получают ambiguous по правилу уникальности строк.

## 6. needs_review и техническое завершение

Для завершённой обработки needs_review = true при любом из условий:

1. missing у обязательного поля заявки или строки.
2. ambiguous или conflict у любого поля, включая необязательное.
3. invalid_value, unverified_source либо unsupported_content.
4. Отсутствие позиций.
5. Не хватает требуемого типа документа.
6. Тип документа не определён либо несколько файлов претендуют на один требуемый тип.

Отсутствие необязательного contact_email не создаёт проблему.
Проблемы имеют стабильный код, путь к полю, описание и связанные источники.
Примеры: required_missing / requested_completion_date;
conflicting_values / requested_completion_date; invalid_value / items[0].quantity.

processing_status = completed означает только технически завершённую обработку.
needs_review = false означает отсутствие проблем по автоматическим правилам,
а не подтверждение человеком. Любой итоговый DOCX требует проверки сотрудником.

Недоступность LLM после исчерпания ограниченных повторов либо критическая ошибка чтения:
processing_status = failed, явная техническая ошибка, запись ошибки в audit,
генерация DOCX запрещена независимо от needs_review. Флаг needs_review не заменяет
технический статус; бизнес-результат такого запуска не считается завершённым.

## 7. Два выходных DOCX

Один ProcessingResult и run_id используются для рабочей заявки и отчёта проверки.
Повторного извлечения или вызова LLM нет. Разрешения, metadata и проверка реальных
байтов перед экспортом применяются независимо к каждому артефакту.

### Рабочая заявка

Заголовок, статус, подтверждённые данные заказчика, название заявки и желаемая дата,
описание, таблица позиций и краткий блок «Требует уточнения». Таблица содержит
наименование, количество, нормализованную единицу; код — только если он имеется.
Частичные позиции сохраняются с незаполненными непригодными ячейками.

При отсутствующем названии печатается «Название заявки: ________________________________»;
при отсутствующей дате — «Желаемая дата завершения: __.__.____». Рядом поясняется,
что значение отсутствует в источниках и заполняется вручную. При conflict или ambiguous
поле остаётся пустым с просьбой сверить источники или уточнить значение. При invalid_value
поле или ячейка не заполняется как достоверная; исходное значение и причина приводятся
в замечаниях. Ручное редактирование Word не изменяет сохранённые состояния приложения.

Замечания к позициям привязаны к номеру, подтверждённому наименованию и полю.
Повторы объединяются только внутри одной позиции. Технические коды, координаты,
подробные кандидаты и audit в рабочую заявку не включаются.

При needs_review = true под заголовком и в верхнем колонтитуле:
«ЧЕРНОВИК — ТРЕБУЕТ ПРОВЕРКИ», имя work_request_needs_review.docx.
Иначе имя work_request.docx; статус указывает на автоматическое формирование
и необходимость проверки человеком. Это не человеческое одобрение.

### Отчёт проверки

Имя verification_report.docx. Содержит идентификатор запуска, входные документы,
статус/needs_review, значения и состояния, проблемы, всех кандидатов и результаты
нормализации, ссылки на доказательства и итог о необходимых действиях человека.
Для единиц видны исходное и итоговое обозначения.

В едином перечне каждый уникальный источник печатается как «Источник N» с файлом,
координатами и полным фрагментом. Объединяются только совпадающие документ, координаты
и текст; одинаковые тексты разных документов сохраняются раздельно. Кандидаты и поля
ссылаются на эти записи, сами кандидаты не удаляются. Неподтверждённые ссылки вынесены
в отдельную группу и не называются проверенными доказательствами. Все идентификаторы
фрагментов, коды проблем и полный снимок audit на момент формирования сохраняются
в разделе технических подробностей. Последующие скачивания дополняют audit приложения.

Provenance подтверждает происхождение и соответствие правилам обработки, а не
истинность исходных сведений. При completed с диагностическими данными отчёт
разрешён даже без содержательных данных для заявки; запрет пустой заявки сохраняется.
При failed генерация и экспорт обоих файлов запрещены.

В каждом комплекте: customer.pdf, description.docx, items.xlsx. Данные синтетические.

Обязательные проверки:

- Ровно три ожидаемых смысловых типа; позиции в исходном порядке, без добавленных строк.

- Каждый DOCX содержит указание на обязательную проверку человеком.
- Сравниваются значения, состояния, источники и содержимое DOCX, а не бинарное равенство файлов; ID и время запуска не фиксируются.

## 10. T — технический acceptance test

Параметризованный сценарий с двумя вариантами:

- T1: корректный комплект A; адаптер LLM недоступен, допустимые повторы исчерпаны.
- T2: комплект A с критической ошибкой чтения одного входного файла (например, повреждённого DOCX).

В обоих вариантах ожидается:

1. processing_status = failed.
2. Пользователь получает явную техническую ошибку соответствующего этапа.
3. Audit содержит ошибку, этап и ID запуска; секреты в журнал не попадают.
4. Генерация запрещена, попытка генерации отклоняется; готовый DOCX отсутствует.
5. Ошибка не представлена как успешный результат с обычным required_missing.

Для T1 ошибка относится к обращению к LLM; для T2 — к parsing. Проверяются оба варианта.
Тесты используют контролируемые сбои, не требуют реального отключения внешнего сервиса.

## 11. Дополнительные проверки правила unverified_source

| Подтверждённые кандидаты после исключения неподтверждённых | Состояние | value |
|---|---|---|
| Нет | missing | None |
| Одно значение либо равные значения | found | Подтверждённое значение |
| Несколько допустимых трактовок без доказанного конфликта | ambiguous | None |
| Разные однозначные значения | conflict | None |

Во всех строках остаётся ValidationIssue(unverified_source), needs_review = true;
неподтверждённый кандидат не может стать итоговым значением. Для обязательного missing
дополнительно действует required_missing. Эти проверки дополняют A/B/C/T, не добавляя
новых бизнес-workflow.
