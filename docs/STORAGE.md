# Локальное хранение

Этап 8 добавляет offline-команды backup/verify-backup/restore без изменения схемы
SQLite. Основной backend удерживает локальный DataLease в lifespan; операции и
SQLite-доступ участвуют в нём. Обслуживание требует эксклюзивной блокировки, исходник
читается без миграций и startup recovery. Копия SQLite создаётся штатным backup API,
зарегистрированные файлы — новыми байтовыми копиями. Restore публикует новый каталог
после проверки manifest, SHA-256 и прежних доменных инвариантов. Подробности:
BACKUP_AND_RECOVERY.md. Текущие fingerprints и физические файлы источника не меняются.

Этап 7B добавляет artifact_writes и частичный UNIQUE-индекс одного prepared на
run_id/вид DOCX. Намерение сохраняется до временного файла; committed, метаданные,
snapshot и дополняемый audit фиксируются одной SQLite-транзакцией после проверки
конечных байтов. Неопределённая файловая операция остаётся prepared и требует
явного восстановления с изоляцией байтов; автоматического признания успеха нет.
Исправный DOCX повторно используется без перезаписи. Прежние metadata сохраняются
в истории явного ремонта. Старые snapshots и v1/v2 fingerprints не мигрируют.
Подробный протокол и границы гарантий: ARTIFACT_RECOVERY.md.

Этап 7A добавляет run_requests: постоянное резервирование ключа и run_id, fingerprint
содержимого, retry_of и состояние операции вне бизнес-snapshot. UNIQUE key_sha256
исключает второй запуск для ключа. Резервирование и llm_runs создаются одной
транзакцией; snapshot и терминальное состояние запроса также коммитятся вместе.
Старые таблицы и результаты не переписываются. Прерванное резервирование не удаляется:
после рестарта возвращается failed без повторного обращения к провайдеру.
Правила: SAFE_RETRIES_AND_IDEMPOTENCY.md. Не запускайте два backend на одном data.
Новый необязательный http_status в ledger сохраняет прежнюю сериализацию при null.

Этап 6 добавляет llm_runs и llm_attempts в прежнюю SQLite без переписывания
бизнес-таблиц/snapshots. Ключ (run_id,attempt_no), отдельные транзакции и digest
защищают учёт от случайного повторного сохранения и порчи. Незавершённые попытки
после рестарта — interrupted с неизвестной стоимостью. Подробности: COST_METRICS.md.

20.10.2026: новые результаты API содержат contract_version=2.0. Отсутствие поля
означает v1. Сериализация v1 сохраняет прежние канонические байты и fingerprints;
PDF line/column добавляются только при фактическом наличии координат v2.
Версия находится внутри защищённого digest snapshot; на этапе форматов v2 схема
SQLite не менялась. Последующий этап 6 добавляет только таблицы метрик, указанные выше.
Проверяются совместное чтение v1/v2, прежние байты DOCX и дополняемый audit после
рестарта. Сам этап форматов не исправлял разрыв записи файла и SQLite commit;
обработка этого окна добавлена этапом 7B, без общей транзакции с файловой системой.

Один процесс backend сохраняет `data/workflow.sqlite3`, исходники, рабочую заявку
и отчёт проверки DOCX. SQLite содержит результаты Pydantic, manifest исходников
с SHA-256, metadata документов и двух независимых артефактов, последовательность
audit. Транзакции и foreign keys связывают данные с запуском. Audit дополняется,
бизнес-результат не переписывается.

Проверяются digest снимка, соответствие audit/metadata и байты исходников перед
генерацией. Экспорт каждого DOCX независимо проверяет файл относительно одного
неизменного результата и run_id. Прерванные до сохранения результата запуски после
рестарта получают failed.

Это проверка случайного повреждения, не криптографическая защита от администратора
с доступом к диску. Один backend, без нескольких workers. Каталог data приватный,
не включается в Git. Для удаления демо-данных остановите сервис и удалите весь
каталог data; автоматическая политика retention в MVP отсутствует.
Хранятся необходимые исходники и provenance, но не ключи, prompts или ответы LLM.

## Этап 9: отдельные решения оператора

`acceptance_events(run_id, sequence, record, digest)` — добавочная таблица с FK на
`runs` и PK `(run_id, sequence)`. Приложение вставляет только новые переходы
accepted/revoked, не обновляет и не удаляет прежние события. Повтор текущего решения
не вставляет строку. Digest-цепочка, последовательность и fingerprint проверяются
перед чтением и фиксацией нового события; сбой транзакции не оставляет отметку.
Бизнес-snapshot и его audit остаются прежними. Сводка читает результаты, журнал
расходов и журнал решений в одной read-транзакции SQLite. Старые копии без таблицы
совместимы для чтения; рабочий ResultStore добавляет пустую таблицу через CREATE
TABLE IF NOT EXISTS. Подробнее: [BUSINESS_METRICS.md](BUSINESS_METRICS.md).
