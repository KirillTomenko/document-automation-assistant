# Согласованность DOCX и SQLite — этап 7B

Числа тестов в исторических разделах относятся к соответствующему этапу; текущая проверка кандидата — [RELEASE_CANDIDATE_REPORT.md](RELEASE_CANDIDATE_REPORT.md).

Два независимых артефакта: рабочая заявка (`document`) и отчёт проверки (`report`).
Генерация и восстановление используют сохранённый бизнес-результат и не вызывают
LLM. Контракты work_request/1.0 и 2.0, fingerprints, provenance и старый audit
сохраняются. SQLite расширяется только таблицей artifact_writes и индексом.

## Протокол записи

1. Проверяются разрешение генерации и SHA-256 зарегистрированных исходников.
   Исправный ранее подтверждённый DOCX возвращается без перезаписи, нового файла
   и нового события generated. Решение о разрешении дополняет audit.
2. DOCX создаётся в памяти и проходит прежнюю проверку содержимого, run_id,
   fingerprint, шаблона/снимка аудита и SHA-256.
3. До записи файла SQLite сохраняет намерение artifact_writes: operation_id,
   run_id, вид, имя, SHA-256 бизнес-результата и ожидаемых байтов, прежние метаданные,
   время UTC, состояние prepared. UNIQUE-индекс разрешает одно prepared на вид и запуск.
4. Файл эксклюзивно создаётся в каталоге запуска как `.<kind>-<operation_id>.tmp`.
   Выполняются flush/fsync и повторная проверка прочитанных с диска байтов.
5. На той же локальной файловой системе создаётся конечное имя через os.link,
   затем временное имя удаляется. Создание ссылки не заменяет существующий файл.
   Если конечное имя занято, публикация отказывается от выполнения.
6. Конечные байты проверяются ещё раз, включая проверку внутри ResultStore.save.
   Одной SQLite-транзакцией фиксируются метаданные артефакта, snapshot, новые
   события audit и состояние намерения committed. Без этой транзакции новый DOCX
   не считается подтверждённым. Изменение метаданных без намерения отклоняется.

Это **не общая атомарная транзакция SQLite и файловой системы**. Между шагами
остаются окна сбоя; журнал позволяет распознать их и безопасно остановиться.
Временный файл находится на том же томе. Нужна файловая система с поддержкой
hard links (проверено на локальном томе Windows); небезопасного fallback через
replace или копирование поверх существующего файла нет.

## Что видно после сбоя и рестарта

| Граница сбоя | Состояние | Действие |
|---|---|---|
| До намерения | Нет новой операции или метаданных | Обычная генерация допустима |
| До временного файла, но после намерения | prepared, файла может не быть | Явное восстановление |
| После частичной/полной записи временного файла | prepared, временные байты не выдаются | Изоляция и новая генерация |
| После публикации, до SQL commit | prepared, конечный файл без новых метаданных | Не выдаётся; явное восстановление |
| Ошибка SQL или rollback после SQL-обновлений | prepared; старый snapshot сохранён | Явное восстановление |
| Commit прошёл, HTTP-ответ потерян | committed и проверяемые байты | Повтор вернёт готовый DOCX |
| Подтверждённый файл отсутствует/повреждён | Исторические метаданные сохранены; статус damaged | Экспорт запрещён; явное восстановление |

При старте prepared сохраняется: приложение не завершает такую генерацию автоматически
и не признаёт найденные байты успешными. При первом запросе состояния/генерации/экспорта
журнал и файлы проверяются заново. Даже структурно корректный DOCX без подтверждённых
метаданных остаётся неподтверждённым. Существующие legacy-файлы с корректными
метаданными доступны без переписывания и без добавления фиктивной истории.

`processing_status=completed` относится к обработке входных данных, а не к готовности
каждого DOCX. Не используйте наличие поля generated_document/generated_report как
доказательство текущей доступности файла: это ожидаемые сохранённые метаданные,
которые остаются историей при внешнем повреждении или удалении. Текущую доступность
показывает GET /runs/{run_id}/artifacts; экспорт всегда независимо проверяет байты.

Статусы каждого вида: not_generated, verified, recovery_required, damaged;
verified=true означает наличие подтверждённых и проверенных байтов. При исправном
основном файле и оставшемся временном файле возможны recovery_required и verified=true:
готовый документ доступен, остатки нужно явно изолировать.

Основные коды: artifact_recovery_required, artifact_damaged,
artifact_verification_failed, artifact_path_unsafe, artifact_recovery_conflict.
HTTP 409 запрещает небезопасную операцию; ошибка файловой системы или SQLite даёт
503. Не считайте 503 доказательством отката: сначала проверьте состояние и повторите
обычный запрос. Повреждённый журнал даёт storage_integrity и не обходится новым выпуском.

## Как восстановить через интерфейс

1. Откройте сохранённый запуск (повтор «Обработать» с теми же файлами возвращает
   прежний run_id благодаря этапу 7A).
2. Если файл исправен, «Подготовить…» повторно использует его; скачивание проверяется
   отдельно. Другой DOCX остаётся независимым и доступным.
3. При предупреждении нажмите **«Восстановить рабочую заявку»** или
   **«Восстановить отчёт проверки»**. Это явное согласие изолировать проблемные
   байты и заново подготовить выбранный DOCX из сохранённых данных.
4. После успеха нажмите «Подготовить…» и скачайте документ. Проверьте его перед
   использованием. Восстановление не снимает needs_review и не означает утверждения.

Неподтверждённые временные/конечные файлы и повреждённые байты перемещаются через
создание ссылки и удаление исходного имени в `<data>/<run_id>/.artifact-recovery/`.
Имя содержит operation_id и прежнее имя файла. Байты не удаляются; это изоляция,
**не резервная копия**. Старое намерение становится abandoned в одной транзакции
с событием начала явного восстановления; затем создаётся новое намерение и DOCX.
Терминальная ошибка обработки не добавляется к completed бизнес-результату.

Повтор самого восстановления безопасен и после сбоя изоляции: совпадение двух
имён проверяется через samefile. Если это разные файлы, система останавливается
с artifact_recovery_conflict, ничего не заменяя. Исправный подтверждённый файл
не перемещается даже при очистке оставшегося временного файла.

После повреждения новый выпуск может иметь другой SHA-256 (включая ZIP timestamps).
Отчёт проверки получает новый снимок дополняемого аудита. Прежние метаданные остаются
в журнале нового намерения, имеющиеся повреждённые байты — в изоляции. Бизнес-значения,
источники и fingerprint не меняются. Это повторное формирование из сохранённых данных,
а не восстановление побитовой копии утраченного файла.

## Проверка и восстановление через локальный API

В PowerShell замените значение run_id на ID из технических подробностей запуска:

```powershell
$artifactRunId = 'ID_ЗАПУСКА'
Invoke-RestMethod "http://127.0.0.1:8000/runs/$artifactRunId/artifacts"
Invoke-RestMethod -Method Post "http://127.0.0.1:8000/runs/$artifactRunId/document/recover"
Invoke-RestMethod -Method Post "http://127.0.0.1:8000/runs/$artifactRunId/verification-report/recover"
```

Два последних действия независимы: выполняйте только нужное. Существующие
POST/GET /runs/{id}/document и /verification-report сохраняют форму успешного ответа.
Обычная генерация повреждённого/неподтверждённого файла теперь честно отказывает,
вместо незаметной замены. Новые маршруты не разрешают редактирование бизнес-данных.

Если исходники недоступны или их SHA-256 изменён, генерация/восстановление блокируются
прежней проверкой. Уже корректный DOCX можно скачать независимо. Если повреждены
SQLite, журнал, права доступа или обнаружены ссылки/junctions, не редактируйте БД
и не удаляйте файлы наугад: остановите backend и сохраните каталог для диагностики.
Автоматическое исправление неоднозначных данных не реализовано.

## Демонстрация и ограничения

```powershell
$env:PYTHONPATH = 'src'
python -B scripts/demo_artifact_recovery.py --output tmp/artifact-recovery-demo
```

Синтетический пример внедряет ошибку SQL после публикации отчёта, перезапускает
сервис, проверяет отказ выдачи неподтверждённого отчёта, явно восстанавливает его
и сравнивает байты ранее готовой рабочей заявки. summary.json содержит фактические
результаты локального прогона; внешних API-вызовов нет.

Проверено 20.10.2026: 588 тестов полной регрессии и 2 дополнительных SQL-fault теста
прошли; все 590 тестов текущего дерева, включая 50 новых для 7B. Дополнительные
тесты добавлены после начала полного прогона, код реализации между проверками
не менялся. Ruff, check_repository.py и git diff --check прошли.

Один процесс backend на приватный локальный data, без нескольких workers.
Не перемещайте файлы параллельно с работой приложения. Каталог и изоляция содержат
копии документов: ограничьте доступ к ним. Они исключены из Git; облачная отправка,
автоматическое удаление изоляции не реализуется. Offline backup/restore добавлены
последующим этапом 8: BACKUP_AND_RECOVERY.md. Backup требует завершённых локальных
операций; байты изоляции не копируются, история artifact_writes сохраняется в SQLite.

Проверены программные сбои и прерывания на предусмотренных границах. Защита от
полного отказа диска, потери питания, повреждения аппаратного кэша и злонамеренного
администратора не обещается. fsync файла не доказывает сохранность directory entries
и SQLite при любой аварии питания. После внешнего удаления исходников или DOCX
утраченные исходные байты без backup вернуть нельзя.
