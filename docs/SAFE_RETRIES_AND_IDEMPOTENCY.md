# Безопасные повторы: этап 7A

Один backend-процесс, один локальный каталог данных, существующая SQLite.
Бизнес-контракты work_request/1.0 и 2.0, сохранённые результаты, fingerprints
и старый audit не меняются. Новая таблица run_requests добавляется без разрушительной
миграции. Backup/restore и согласование DOCX с SQLite реализованы отдельно; см. BACKUP_AND_RECOVERY.md и ARTIFACT_RECOVERY.md.

## Один запрос приложения

Передайте в POST /runs заголовок `Idempotency-Key`, например `local-action-001`.
Ключ задаёт приложение, не LLM: 1–128 ASCII-символов A–Z, a–z, 0–9, `. _ : -`.
Несколько таких заголовков или некорректный ключ дают 422 idempotency_key_invalid.
В SQLite хранится SHA-256 ключа; срока автоматического удаления нет.

Идентичность запроса включает исходные имена файлов, длину и SHA-256 каждого файла,
число повторяющихся файлов и retry_of. Порядок файлов, форматирование JSON и
представление base64 не определяют идентичность. Имена учитываются до добавления
серверного префикса. Замена байтов, переименование, добавление дубликата или изменение
retry_of под прежним ключом дают 409 idempotency_conflict. Настройки модели, тарифов
и активного контракта не пересчитывают исторический результат при повторе ключа.

| Ситуация | Ответ | Обращение к LLM |
|---|---|---|
| Новый ключ | 201, сохранённый результат completed или failed | Не более одной автоматической попытки |
| Тот же ключ, запрос выполняется | 202, run_id и operation_status | Дополнительного вызова нет |
| Тот же ключ, запрос завершён | 200, существующий результат и run_id | Дополнительного вызова нет |
| Тот же ключ, другое содержимое | 409 idempotency_conflict | Дополнительного вызова нет |
| Заголовка нет | Каждый POST создаёт новый run_id, как прежде | Самостоятельная обработка |

Ответы содержат Location: /runs/{run_id}, Cache-Control: no-store; воспроизведённый
ответ — Idempotency-Replayed: true. GET /runs/{run_id} для активного запуска также
возвращает 202. В этой оболочке нет processing_status=completed: она не является
бизнес-результатом. Полный JSON нужно хранить/показывать только после ответа 200/201.

Клиент должен сохранить ключ **до** отправки и повторять его после сетевой ошибки.
Streamlit использует устойчивый ключ из идентичности файлов и родителя повтора:
обычная кнопка «Обработать», повтор после потери ответа и новая сессия с теми же
файлами возвращают прежний запуск. Для действительно новой обработки после известного
отказа есть отдельная кнопка. Смена имени/содержимого файлов означает новое действие.

## Жизненный цикл и перезапуск

BEGIN IMMEDIATE атомарно резервирует run_id, UNIQUE-хеш ключа, fingerprint и запись
llm_runs **до** записи файлов и ожидания локального lock. Конкурентный повтор читает
резервирование, а не входит в pipeline. Затем регистрируются исходники и состояние
processing. Снимок результата и конечное состояние finished записываются одной
транзакцией. Если этот commit не состоялся, успешный результат не объявляется.

На старте незавершённый запуск становится failed / processing_interrupted, а
незавершённая LLM-попытка — interrupted с неизвестными расходами. Старый ключ остаётся
зарезервированным и возвращает этот отказ; повторное извлечение не запускается.
При повреждении записи операция останавливается с storage_integrity; резервирование
не удаляется. Независимо корректные ранее сохранённые результаты остаются доступны.

Завершённые попытки сохраняются с прежними usage и тарифом; изменение состояния
запроса их не удаляет. Первичный ключ (run_id, attempt_no) и проверка неизменяемости
предотвращают двойной учёт. Отказ сохранения завершения оставляет начальную запись;
после рестарта её расход неизвестен. См. [COST_METRICS.md](COST_METRICS.md).

## Неопределённый исход и явная новая обработка

LLM и неизвестные пользовательские extractors получают одну автоматическую попытку,
включая ошибки схемы, 429 и 500. Настроенный предел attempts применяется только к
явно offline-extractor. Переключения с LLM на demo после ошибки нет.

Тайм-аут, обрыв чтения (включая обрыв после HTTP 200), прерывание процесса, HTTP 408
и 5xx считаются неопределённым исходом. Ответ без подтверждённого completed
(включая in_progress/incomplete) также консервативно блокирует новый вызов,
сохраняя полученный usage. Повтор того же ключа возвращает failed;
новый запрос с retry_of такого запуска получает 409 retry_outcome_unknown без
сетевого вызова. Возможное списание не становится нулевым. HTTP-заголовки сами
по себе не подтверждают получение полного ответа. Exactly-once удалённого вызова
не обещается: провайдер может продолжить работу после локального тайм-аута.

Полученный полный некорректный ответ и подтверждённый HTTP 429 — известные отказы.
Они не повторяются автоматически. Оператор может явно отправить новый POST с новым
ключом и полем `retry_of` прежнего run_id; это новый потенциально платный запуск.
Стоимость HTTP-отказа без usage остаётся неизвестной, даже если исход известен.
Неизвестная стоимость и неизвестный исход — разные признаки.

GET /runs/{run_id}/operation возвращает retry_of, state, can_retry и безопасный
retry_block_reason. Для completed или активного родителя — retry_requires_failed_run;
для отсутствующего — retry_run_not_found. Для legacy-отказа без ledger или повреждения
учёта новая отправка не разрешается. Повтор нового ключа возвращает уже созданного
потомка. В сводках расходы каждого run_id независимы; сумма цепочки включает все
попытки родителя и потомка. retry_calls — повторы внутри одного запуска, не длина цепочки.

## Ограничения

Не запускайте два экземпляра backend или несколько uvicorn workers на одном data.
Восстановление pending выполняется при старте и предполагает остановленный прежний
процесс. SQLite UNIQUE защищает идентичность, но распределённая обработка не поддерживается.

Без ключа и при намеренно другом ключе без retry_of запрос остаётся новым действием:
глобальной дедупликации документов нет. Поэтому блокировка неизвестного родителя
не защищает от намеренного обхода через независимый новый запрос. Истечение ключей,
автоматическое выяснение статуса у провайдера и снятие блокировки не реализованы.
Для неопределённого исхода сначала требуется ручное выяснение у провайдера;
приложение само не выдаёт разрешение на повтор.

Повторное чтение результата, генерация и скачивание двух DOCX не вызывают LLM.
Проверки SHA-256 и прежние разрешения сохранены. Последующий этап 7B добавляет
журнал намерений записи и явное восстановление после сбоя DOCX/SQLite; исправный
DOCX возвращается без пересоздания. Подробности: ARTIFACT_RECOVERY.md. Эти операции
не меняют ключ запроса, retry_of или финансовую историю.

Проверки: tests/test_run_requests.py, mock HTTP и синтетические документы; реальных
платных вызовов нет. Включены конкурентный POST, рестарт, отмена, тайм-аут, разрыв
после заголовков, ошибка commit, порча ledger, явный retry и потеря ответа Streamlit.
