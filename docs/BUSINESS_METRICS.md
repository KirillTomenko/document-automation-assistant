# Принятие результата и экономика обработки

Период первой версии — всё время текущего локального хранилища SQLite, без
фильтров дат. Сводка доступна в Streamlit («Качество и экономика — всё время»)
и через `GET /business-metrics`. Чтение выполняется в одной read-транзакции SQLite.
Метрики не вызывают LLM, не генерируют DOCX и не изменяют результаты.

## Три разных уровня результата

1. Входной файл — одна зарегистрированная загрузка в `inputs`. Одинаковые байты,
   загруженные дважды, дают две входные записи, даже если извлечение дедуплицировало
   документ. Повтор POST с тем же idempotency key не добавляет входных записей.
2. `completed` — технически завершённый запуск обработки комплекта. Он может иметь
   пропуски, конфликты, `needs_review=true` и ещё не иметь готовых DOCX.
3. Принято оператором — отдельное явное решение о дальнейшем использовании одного
   `run_id`. Ни completed, ни `needs_review=false` не заменяют это решение.

## Принятие и отзыв

После формирования обоих DOCX нажмите «Проверено и принято для дальнейшей работы».
Сервер заново проверяет completed, отсутствие незавершённой записи каждого артефакта,
наличие файлов, SHA-256 и существующие содержательные инварианты DOCX. При
`needs_review=true` нужно отдельно включить «Замечания needs_review рассмотрены».
Это не снимает needs_review, не исправляет поля и не обходит запреты генерации/экспорта.
Рабочая заявка остаётся черновиком, если так определил бизнес-контракт.

API: `GET /runs/{run_id}/acceptance`, `POST /runs/{run_id}/acceptance` с JSON
`{"remarks_reviewed": true}` (для чистого результата достаточно `{}`),
`POST /runs/{run_id}/acceptance/revoke` — явный отзыв. Повтор принятия в принятом
состоянии и повтор отзыва в отозванном состоянии не создают событий. После отзыва
можно принять снова; прежняя история остаётся. Конкурирующие запросы сериализуются
существующей блокировкой однопроцессного сервиса и транзакцией SQLite.

Отметка означает подтверждение оператором дальнейшего использования, а не юридическое
утверждение, согласование заказчиком или доказанную безошибочность. Нет учётных записей
операторов: приложение локальное и однопользовательское.

История — отдельная таблица `acceptance_events`: run_id, последовательность, время UTC,
принятие/отзыв, подтверждение рассмотрения замечаний, fingerprint бизнес-результата,
SHA-256 обоих DOCX на момент принятия, digest события и предыдущего события.
Приложение только добавляет события. Snapshot, audit обработки, provenance, fingerprints
и контрактные поля v1/v2 не меняются. Проверяются последовательность, переходы состояний,
цепочка и соответствие бизнес-результату. Это не защита от администратора, напрямую
переписывающего SQLite; журнал не имеет внешней цифровой подписи.

Принятие относится к неизменяемому результату запуска. Позднее повреждение или явное
восстановление DOCX **не отзывает решение автоматически**: история хранит доказательства
на момент принятия. Доступность текущих файлов проверяется отдельно; UI показывает
предупреждение, экспорт по-прежнему отклоняет повреждённый файл. Для пересмотра решения
используйте отзыв, проверку восстановленных документов и новое принятие.

## Показатели и знаменатели

| Показатель API | Определение |
| --- | --- |
| total_runs | Все уникальные run_id в runs, включая failed и незавершённые |
| completed_runs / completed_share | Число completed / total_runs |
| failed_runs | Число сохранённых результатов failed |
| unfinished_runs | total_runs − completed_runs − failed_runs; ещё нет сохранённого результата |
| needs_review_runs | Сохранённые результаты с needs_review=true; принятие их не исключает |
| registered_inputs | Все строки inputs всех запусков, включая failed |
| successful_inputs / successful_input_share | Зарегистрированные файлы completed-запусков, имеющие подтверждение SHA в metadata результата / registered_inputs |
| runs_without_registered_inputs | Запуски без зарегистрированных файлов; их неизвестное число файлов не выдумывается и не входит в файловый знаменатель |
| llm_attempts | Все уникальные (run_id, attempt_no) из постоянного журнала, включая failed/interrupted/started и not_sent |
| retry_calls | Попытки с request_state≠not_sent, у которых attempt_no>1 **или** run.retry_of задан; одна попытка считается один раз |
| unknown_cost_attempts | Попытки с estimated_cost=null, включая тайм-ауты и отсутствие тарифа/usage |
| untracked_runs | Запуски без meter либо с mode=untracked: число старых вызовов и расходы неизвестны |
| known_estimated_costs | Сумма известных оценок попыток отдельно по каждой валюте; включает расходы failed-запусков |
| tariffs | Использованные сохранённые тарифы: провайдер/модель, версия, дата, источник, валюта и цены за миллион токенов; не текущие цены из интернета |
| simulated_runs | Запуски с meter.data_origin=simulated, то есть mock HTTP; общая сводка с ними помечается демонстрационной |
| accepted_results | Число запусков, последнее событие которых accepted; отозванные не входят |
| average_cost_per_accepted | Полная известная сумма LLM API всех запусков / accepted_results, если расчёт допустим |

Доли возвращаются от 0 до 1; Streamlit показывает проценты. При нулевом знаменателе
доля отсутствует («Недостаточно данных»), а не равна нулю.

Файловая доля — консервативный показатель прохождения workflow, **не точность извлечения**.
В failed-запуске даже прочитанные файлы не считаются успешно обработанными. Частичные
поэтапные успехи файлов старый snapshot не хранит; они не реконструируются по косвенным
признакам. Разная величина комплектов означает, что доля файлов отличается от доли запусков.
Документ неподдерживаемой структуры может участвовать в completed с needs_review;
содержательное качество оценивает оператор. Для доказательства точности нужен отдельный
размеченный набор, который эта сводка не заменяет.

## Стоимость принятого результата

Числитель: сумма `estimated_cost` **всех** попыток всех запусков текущего хранилища,
в том числе неудачных, явных повторов и непринятых результатов. Знаменатель: текущее
число принятых и не отозванных результатов. Отзыв уменьшает знаменатель, но не удаляет
ранее понесённые расходы. При нескольких исторических попытках в одном запуске каждая
учитывается один раз по первичному ключу; повтор запроса/чтения/скачивания не добавляет расход.

Точная средняя **не показывается**, если:

- нет принятых результатов (`no_accepted_results`);
- есть хотя бы одна неизвестная стоимость или untracked-запуск (`unknown_cost`);
- известные расходы имеют несколько валют (`multiple_currencies`).

В этих случаях UI пишет «Недостаточно данных», объясняет причину и отдельно показывает
известные суммы и число неопределённых попыток. В legacy/untracked число неизвестных
попыток само неизвестно: счётчик unknown_cost_attempts не выдаётся за их полный подсчёт.
Тарифная единица существующего журнала фиксирована: цена за миллион input/output/cached
токенов. Разные версии тарифов в одной валюте можно суммировать **после** расчёта каждой
попытки по её сохранённому тарифу. Конвертации валют и усреднения цен токенов нет.

Offline даёт 0 LLM-попыток и 0 расходов **на LLM API**. При только offline-запусках
и хотя бы одном принятом результате средняя API равна 0 без выдуманной валюты.
Это не нулевая стоимость обработки: время оператора, разработка, оборудование,
хранение и эксплуатация не измеряются. Оценка по тарифу не равна подтверждённому
списанию провайдера. Правила usage и тарифов: [COST_METRICS.md](COST_METRICS.md).

## Перезапуск и резервная копия

Таблица создаётся добавочно, без изменения старых строк. Все решения и расходы
переживают рестарт. Полная SQLite уже входит в backup, поэтому протокол копирования
не менялся; проверка допустимой схемы дополнена acceptance_events и её валидатором.
Backup этапа 8 без этой таблицы также читается; при запуске восстановленной рабочей
копии добавляется пустая таблица. Старые версии приложения этапа 8 новую таблицу
не знают: используйте текущую версию для проверки новых копий.
Порядок команд и защита доступа: [BACKUP_AND_RECOVERY.md](BACKUP_AND_RECOVERY.md).

## Синтетическая демонстрация и коммерческий разговор

Запуск без платных запросов (PowerShell, из корня проекта):

```powershell
$env:PYTHONPATH = 'src'
python -B scripts/demo_business_metrics.py --output tmp/stage9-demo
```

Каталог должен быть новым. Скрипт использует синтетические файлы, mock HTTP и условный
тариф из example-конфигурации; создаёт сводку, проверяет принятие/отзыв, отказ при
неизвестной стоимости, backup/restore и реальные локальные HTTP-запросы к восстановленному
приложению. JSON-отчёт явно помечен как демонстрационный, а не оплаченные расходы.

Фактически проверенный пример: сначала 3 запуска, 2 completed (66,7%), 1 failed,
1 needs_review, 4 успешных файла из 5 (80%), 2 mock LLM-попытки, 1 повторное
обращение через retry_of, 2 принятых результата. При **условном** тарифе
synthetic-example-v1: 0,0368 RUB известных расходов / 2 = 0,0184 RUB на принятый
результат. После добавления mock-тайм-аута: 4 запуска, 2 completed (50%), 2 failed,
4 успешных файла из 6 (66,7%), 3 LLM-попытки, 1 с неизвестной стоимостью.
Известная часть остаётся 0,0368 RUB; средняя отсутствует. Это демонстрация формул,
а не оплаченная стоимость или доказательство экономии на реальных документах.

В этом сценарии также фактически выполнены CLI backup → verify-backup → restore,
запуск отдельного backend с восстановленными данными и HTTP-чтение прежних run_id,
решений, usage, retry_of и обоих DOCX. Сохранены 4 события принятия/отзыва;
SHA-256 всех 6 исходников и 4 DOCX совпали. Платных обращений к провайдеру — 0.

В коммерческом разговоре можно назвать проверенное число запусков, документов,
отказов, принятых результатов и оценку API по явно названному тарифу. Укажите период,
размер и происхождение выборки, наличие неизвестных расходов и ограничения структур.
Нельзя выводить из completed/принятия процент безошибочности, гарантированную экономию,
окупаемость или замену сотрудника. Экономия времени требует сравнения одинаковых задач
с ручной работой, измерения времени проверки и исправлений; таких измерений здесь нет.
