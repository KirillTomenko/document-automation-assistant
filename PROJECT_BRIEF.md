# Document Automation Assistant — Project Brief

## 1. Цель проекта

Создать законченный портфельный MVP для автоматизации работы с разнородными
бизнес-документами.

Проект должен демонстрировать не просто использование LLM, а полный
контролируемый бизнес-процесс:

PDF / DOCX / XLSX
→ определение типа документа
→ извлечение данных
→ структурирование
→ валидация
→ needs_review при сомнениях
→ заполнение шаблона
→ готовый DOCX
→ указание источников данных.

Основная ценность для заказчика:
сокращение ручного переноса информации из документов и подготовка
готового черновика документа для проверки сотрудником.

Проект создаётся прежде всего как коммерческий кейс для портфолио,
фриланс-площадок и прямых предложений бизнесу.

---

## 2. Целевая аудитория

Малый и средний бизнес, где сотрудники регулярно:

- получают PDF, DOCX и XLSX;
- вручную ищут в них нужные данные;
- переносят сведения в стандартные Word-шаблоны;
- проверяют комплектность документов;
- формируют заявки, отчёты, коммерческие предложения, анкеты и заключения.

---

## 3. Основной демонстрационный сценарий MVP

Пользователь загружает несколько документов разных типов.

Например:

- PDF с исходной информацией;
- DOCX с описанием;
- XLSX с параметрами;
- Word-шаблон итогового документа.

Система:

1. определяет тип каждого документа;
2. извлекает текст и структурированные данные;
3. приводит сведения к единой Pydantic-схеме;
4. проверяет обязательные поля;
5. обнаруживает отсутствующие или противоречивые данные;
6. не придумывает отсутствующую информацию;
7. выставляет needs_review там, где нужна проверка человека;
8. формирует итоговый DOCX по шаблону;
9. показывает, из какого документа было получено каждое ключевое значение;
10. сохраняет журнал обработки.

Человек принимает окончательное решение и проверяет итоговый документ.

---

## 4. Ключевые принципы

### Human-in-the-loop

AI не должен самостоятельно принимать ответственные бизнес-решения.

Если данных недостаточно, результат должен иметь статус needs_review.

### No hallucinations

Нельзя заполнять отсутствующие данные предположениями.

Допустимые состояния поля:

- значение найдено;
- значение отсутствует;
- значение неоднозначно;
- обнаружено противоречие.

### Structured output

LLM должен возвращать строго структурированные данные.

Использовать:

- Pydantic;
- JSON Schema;
- валидацию результата;
- controlled retry при ошибке структуры.

### Traceability

Для важных извлечённых данных нужно хранить:

- исходный файл;
- страницу / лист / раздел, если возможно;
- исходный фрагмент;
- итоговое значение.

### Audit log

Фиксировать:

- входные документы;
- этапы обработки;
- ошибки;
- использование модели;
- needs_review;
- результат генерации.

Не хранить секреты или ненужные персональные данные.

Backend:
- Python
- FastAPI
- Pydantic

Интерфейс MVP:
- Streamlit либо простой web UI

- pytest

Контейнеризация:

## 6. MVP — что обязательно должно работать

Поддержка:

- текстовых PDF;
- DOCX;
- XLSX;
- Word-шаблона результата.

Обязательные функции:

- загрузка нескольких файлов;
- классификация документов;
- извлечение данных;
- единая структурированная схема;
- проверка обязательных полей;
- needs_review;
- обнаружение противоречий;
- генерация DOCX;
- provenance / источники значений;
- audit log;
- обработка ошибок;
- минимальный web-интерфейс;
- автоматические тесты.

---

## 7. Что НЕ делать в первой версии

Не добавлять без необходимости:

- OCR рукописных документов;
- сложный multi-user режим;
- enterprise RBAC;
- SAP / 1C / CRM интеграции;
- MCP-интеграции;
- массовую обработку десятков тысяч документов;
- сложную векторную БД;
- мультиагентную архитектуру;
- автономную отправку писем или внешние действия;
- мобильное приложение.

Эти возможности могут появиться позже.

Главная задача MVP — один полностью работающий документный workflow.

---

## 8. Демонстрационные данные

Использовать только синтетические или обезличенные документы.

Подготовить небольшой набор, например:

- 10–20 входных документов;
- 3 типа документов;
- один итоговый Word-шаблон;
- несколько случаев с отсутствующими данными;
- несколько случаев с противоречиями.

Не использовать реальные конфиденциальные документы заказчиков.

---

## 9. Definition of Done

MVP считается готовым, если можно провести демонстрацию:

1. открыть приложение;
2. загрузить несколько документов;
3. нажать "Обработать";
4. увидеть извлечённые данные;
5. увидеть источники;
6. увидеть warnings / needs_review;
7. сформировать итоговый DOCX;
8. скачать документ;
9. открыть его и убедиться, что шаблон заполнен корректно.

Дополнительно:

- основные сценарии покрыты тестами;
- README позволяет запустить проект локально;
- отсутствуют секреты в репозитории;
- есть демонстрационный набор файлов;
- есть короткое демо для GitHub / Telegram / откликов.

---

## 10. Коммерческое позиционирование

Рабочая формулировка:

"Автоматизация обработки документов:
AI извлекает данные из PDF, Word и Excel,
проверяет комплектность, отмечает спорные места
и формирует готовый Word-документ для проверки сотрудником."

Продавать нужно не LLM и не RAG, а результат:

"меньше ручного переноса данных и меньше времени на подготовку документов".

---

## 11. Связь с другими проектами

Этот проект должен оставаться универсальным.

Проект подготовки заявок Сколково рассматривается как отдельный будущий
use case Document Automation Assistant, а не как основная логика системы.

В дальнейшем возможны сценарии:

- заявка Сколково;
- коммерческое предложение;
- анкета;
- тендерная документация;
- обработка замечаний;
- отчёт;
- договорный workflow.

Не переносить специфическую бизнес-логику Сколково в ядро проекта,
пока не станет понятно, какие компоненты действительно универсальны.

---

## 12. Архитектурный принцип

Предпочтительный pipeline:

ingestion
→ parsing
→ classification
→ extraction
→ normalization
→ validation
→ review
→ document generation
→ audit

Каждый этап должен быть максимально независимым.

Бизнес-логика, LLM-провайдер и пользовательский интерфейс
не должны быть жёстко связаны между собой.
